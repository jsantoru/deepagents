Architecture Spec

API-First Rewrite Specification

This document defines a ground-up rewrite of DeepAgents where durable execution comes first, the event log is canonical, phase 1 ships as API-only, and phase 2 adds a UI as a consumer of the same HTTP and SSE contracts.

Purpose

This rewrite has four goals:

  1. Make agent execution independent from any UI transport.
  2. Make the event log the primary source of truth.
  3. Ship an API-only system in phase 1.
  4. Add a UI in phase 2 as a pure consumer of the API and event stream.

Executive Summary

The rewritten system revolves around five durable concepts:

  • conversation
  • turn
  • run
  • event
  • artifact

Phase 1 exposes these through a clean HTTP API and durable execution model. Phase 2 adds a frontend that reads the same data and attaches to SSE streams for live updates.

Design Principles

  1. Execution is primary.
  2. Event log is the source of truth.
  3. API before UI.
  4. Separation of write and read concerns.
  5. Replaceability at the execution boundary.
  6. Explicit lifecycle states.
  7. Operational honesty.

Non-Goals

Phase 1

  • No web UI
  • No SSE requirement for correctness
  • No multi-tenant billing system
  • No advanced auth provider integration
  • No human-in-the-loop workflow orchestration
  • No vector memory layer

Phase 2

  • No UI-owned execution state
  • No client-side event reconciliation heuristics
  • No bespoke stream protocol separate from the API event model

Architecture Overview

The rewritten platform has four runtime roles:

  1. API service: accepts commands, exposes reads, serves SSE, never owns long-running execution.
  2. Executor: consumes pending runs, invokes the agent stack, emits run events, finalizes outcomes.
  3. Database: stores domain records, event log, attachments, and read-model projections.
  4. Clients: scripts and tests in phase 1, web UI in phase 2.

High-Level Flow

Client submits turn
  -> API persists conversation turn + run request
  -> API marks run pending
  -> API enqueues work
  -> Executor claims run
  -> Executor emits ordered run events
  -> Executor writes final artifacts and terminal status
  -> Clients query state or attach to SSE event stream

Transport Model

  • Point-in-time HTTP reads
  • Paginated event reads
  • SSE tailing of the event stream

All three read from the same persisted state model.

Persistence Model

run_events is the only canonical trace store.

The system must not duplicate the full event stream into a second JSON blob on runs.

Read-model rule

Final answer and metrics may be denormalized for efficient reads, but they are explicitly derived from the event stream and terminal run state.

Recommended database details

  • PostgreSQL primary store
  • payload_json as JSONB
  • metadata_json as JSONB
  • Typed timestamps with timezone

Minimum indexes

  • conversations(created_at desc)
  • turns(conversation_id, sequence)
  • runs(conversation_id, requested_at desc)
  • runs(turn_id, attempt_number)
  • runs(status, requested_at)
  • run_events(run_id, sequence)
  • attachments(turn_id, order_index)

Execution Model

Phase 1 executor

Phase 1 may use a single-process executor if needed for speed, but the seam must be explicit.

Executor responsibilities

  1. Claim one pending run.
  2. Mark it claimed.
  3. Emit run.started.
  4. Execute the agent.
  5. Append events during execution.
  6. Write terminal artifacts.
  7. Mark terminal status.

Claiming protocol

  • SELECT ... FOR UPDATE SKIP LOCKED
  • Lease ownership columns with expiry
  • Unique attempt semantics enforced in DB

Cancellation

  1. API marks cancel_requested.
  2. Executor checks cooperative cancellation state.
  3. Executor emits run.cancel_requested.
  4. Executor emits run.cancelled on success.

Timeouts

  • Light mode: 2 minutes
  • Standard mode: 10 minutes

Retries

Phase 1 supports explicit retry by creating a new run attempt for the same turn. Automatic retry should be limited to transient infrastructure failures.

SSE rule

Use a single SSE event name, run_event, and keep the semantic event type inside the JSON payload. That keeps JSON history and SSE structurally identical.

Agent Integration

The deepagents integration must be isolated behind one adapter.

AgentAdapter responsibilities

  1. Build agent request payload.
  2. Normalize stream parts into stable internal events.
  3. Aggregate usage across all model invocations.
  4. Normalize tool call envelopes.
  5. Isolate library-specific tuple or object-shape quirks.

Usage accounting

Usage must be summed across the entire run, not just the final message.

Tool accounting

Tool counts must be derived from normalized tool events, not loose message-role checks.

Auth, Validation, and Observability

Authentication

Phase 1 should include at least a basic auth boundary.

  • Minimum acceptable: static bearer token
  • Preferred: principal table with API keys

Validation

  • Pydantic request and response models on the backend
  • Startup validation for required secrets
  • Attachment validation before execution
  • Phase 2 runtime API validation on the frontend

Structured logs

  • conversation_id
  • turn_id
  • run_id
  • status
  • event_sequence when relevant
  • executor_owner when relevant

Metrics

  • Runs created, completed, failed, cancelled
  • Queue depth
  • Run duration
  • Event append latency
  • Event stream attach count
  • Token usage by model
  • Tool call counts by tool

Operations

  • Alembic from day 1
  • No create_all() on startup
  • Explicit retention policy for events and attachments

Phase 2 UI and SSE Design

UI principles

  • The UI consumes HTTP queries for baseline state.
  • The UI consumes SSE for live tailing.
  • The UI must not invent execution state that contradicts backend state.

Recommended frontend modules

  • ConversationListPage
  • ConversationView
  • MessageComposer
  • RunTimeline
  • RunStatusBanner
  • AttachmentPicker
  • AdminDashboard

Recommended hooks

  • useConversationList
  • useConversation
  • useCreateTurn
  • useRun
  • useRunEvents
  • useRunEventStream

SSE contract

The UI should call:

  • GET /v1/runs/{run_id}/events for historical state
  • GET /v1/runs/{run_id}/events/stream?after_sequence=N for live continuation

The UI should not need merge heuristics based on title, content equality, or tool-query extraction from raw strings.

Event rendering guidance

  • run.progress -> progress card
  • run.tool.started -> tool activity row
  • run.tool.completed -> expandable tool result
  • run.message.delta -> incremental assistant body
  • run.completed -> terminal state and final answer

Testing Strategy

Phase 1

  • Run lifecycle transitions
  • Event append ordering
  • Cancellation state transitions
  • Usage aggregation
  • Tool call normalization
  • Create conversation and turn
  • Run executes to completion
  • Historical events query ordering
  • SSE replay and live tailing
  • Retry and cancel flows

Failure tests

  • Executor crash before terminalization
  • Duplicate claim attempts
  • Malformed agent adapter stream payload
  • DB transient failure during event append

Phase 2

  • Render completed conversation from HTTP only
  • Attach to in-progress run via SSE
  • Reconnect using after_sequence
  • Cancel from UI and observe terminal update

Open Questions and Recommended Defaults

Open questions

  1. Should assistant final answers be stored as messages, artifacts, or both?
  2. Should phase 1 support multiple concurrent runs per conversation, or exactly one active run?
  3. Do we want server-side conversation summarization in phase 1?
  4. Should the executor use PostgreSQL-backed claiming only, or adopt a real queue immediately?
  5. What retention policy applies to sensitive attachments?

Recommended defaults

  1. One active run per conversation in phase 1
  2. run_events as the only canonical trace store
  3. Alembic from day 1
  4. API key or bearer-token auth from day 1
  5. OpenAPI-generated client types before phase 2
  6. One stable event envelope for JSON history and SSE
  7. Agent integration isolated behind AgentAdapter

Success criteria

  1. A run completes correctly without any UI connected.
  2. SSE can attach, detach, and reattach without changing execution behavior.
  3. No duplicate trace store exists.
  4. Final answer and metrics can be rebuilt from canonical persisted state.
  5. Phase 2 frontend can be implemented without protocol-merging heuristics.
  6. Executor implementation can change without API contract changes.
  7. Integration tests cover the full phase 1 workflow without browser dependencies.
