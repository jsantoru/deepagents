CODEX 5.5 Revised Plan

API-first rewrite with durable execution and event-log delivery

This plan reconciles the Codex and Claude rewrite specs into a simpler implementation path: build the execution system first, expose it through REST and event polling, then add UI and SSE as views over the same persisted event log.

High-Level Shape

At the highest level, this is not a chat UI with a backend. It is an execution system with optional clients. Clients create work, the executor performs work, and every observable step is persisted before any client sees it.

Responsibilities

  • Clients submit turns and read state.
  • API validates requests, writes intent, and serves reads.
  • Executor claims runs and writes events.
  • PostgreSQL is the durable coordination point.
  • AgentAdapter contains external library behavior.

Core promise

Disconnecting a browser, test runner, or SSE stream must not change run execution. Delivery is a projection; execution is owned by the executor and recorded in PostgreSQL.

Keep It Simple

These rules keep the rewrite from turning into a distributed platform before the core loop is proven.

  1. Build phase 1 without a frontend.
  2. Build phase 1 without SSE.
  3. Use PostgreSQL as the only coordination dependency at first.
  4. Use one event table as the trace source of truth.
  5. Use run_events.id as the cursor.
  6. Allow one active run per conversation in phase 1.
  7. Keep the executor in-process only if it can later move out without changing client APIs.
  8. Prefer explicit SQL read queries over premature read-model tables.
  9. Add artifacts only for terminal outputs that simplify reads.
  10. Do not add Redis, Celery, WebSockets, vector memory, or multi-user billing in the first rewrite pass.

Minimum Viable Phase 1

The smallest useful version is deliberately narrow.

  1. Create a conversation.
  2. Create a turn.
  3. Create one pending run for that turn.
  4. Execute the run in the background.
  5. Persist typed events to run_events.
  6. Poll events by cursor.
  7. Read final answer and metrics after completion.

Durable Domain

The domain has five durable concepts. The important split is turns -> runs: a user submission is stable, while execution attempts can be retried.

Run Lifecycle

The API can request cancellation, but the executor owns terminal status.

Phase 1 can mark active runs failed on process restart. Lease-based recovery is useful later, but it should not block the first API-only rewrite.

Read Paths

There are three read shapes. They should stay separate.

    API --> RunRead["Run reads

    API --> EventRead["Event reads

    ConversationRead --> Tables[("turns, runs, artifacts")]
    RunRead --> Tables
    EventRead --> Events[("run_events")]

Conversation reads do not include full event history. Event reads do not reconstruct final answers. Run reads do not return an unbounded timeline.

Executive Decisions

Keep from Codex

  1. Separate conversation, turn, run, event, and artifact.
  2. Model run as an execution attempt.
  3. Use one stable event envelope.
  4. Isolate deepagents behind AgentAdapter.
  5. Generate frontend types from OpenAPI before phase 2.

Keep from Claude

  1. Phase 1 has no UI or SSE requirement.
  2. Phase 1 uses cursor polling for progress.
  3. No in-memory subscriber queues.
  4. Event cursor is DB-generated.
  5. Conversation detail excludes full event history.
  6. Startup fails on missing secrets.

Revised defaults

separate turns and runs run_events.id cursor phase 1 no SSE phase 2 LISTEN/NOTIFY one active run Alembic first

Execution Design

Phase 1 can use an in-process executor, but it must communicate through PostgreSQL and never through in-memory subscriber queues.

Allowed phase 1 state

  • _running_tasks for local task management
  • executor id for ownership and logs

Disallowed phase 1 state

  • per-subscriber queues
  • event buffers as source of truth
  • HTTP request objects participating in execution

Executor lifecycle

  1. Transition pending to claimed.
  2. Transition claimed to running.
  3. Append run.started.
  4. Load conversation history.
  5. Invoke AgentAdapter.
  6. Append normalized events.
  7. Write final artifacts.
  8. Append terminal event.
  9. Transition to terminal status.

AgentAdapter contract

  • Build prompt context from turn, attachments, and history.
  • Normalize stream output into internal event objects.
  • Aggregate token usage across all model calls.
  • Count tool calls by tool type.
  • Return final answer and metrics.

Success criteria

  1. A run completes with no UI and no stream connected.
  2. Event history is queryable through a cursor.
  3. Final answer and metrics are available after completion.
  4. SSE can be added without changing execution semantics.
  5. Reconnect is event replay after a cursor.
  6. No duplicate trace store exists.
  7. No frontend protocol heuristics are needed.
  8. The executor can later move out of process without changing client APIs.
